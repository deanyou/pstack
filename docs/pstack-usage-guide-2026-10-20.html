PSTACK · Agent Engineering Skills

讓 agent 寫更少、品質更高的程式碼

pstack 把理解、實作、評審與驗證整理成可重複執行的工作流程。先說清楚目標，再用真實輸出驗收，讓平行工作的結果也能逐項查核。

1安裝：先選 harness，再設定模型

pstack 是一套 Agent Skills。這個鏡像把工具名、路徑與模型設定對應到各個 harness；實際能否平行派發、切換模型或訂閱事件，仍取決於執行工具提供的能力。

# 終端：從這個鏡像選擇 skills 與安裝目標
npx skills add deanyou/pstack

安裝後，在聊天輸入 /setup-pstack，選推理預算與各角色的模型。設定對新對話生效；auto 或 inherit-parent 代表沿用主對話模型。評審名單中的每個項目各占一個席位，沿用主模型不會減少席位數。

指令名稱依安裝方式而異：Claude Code 外掛版通常是 /pstack:poteto-mode；直接安裝 skill 可用 /poteto-mode。Pi / OMP 使用 /skill:poteto-mode。以斜線選單實際列出的名稱為準。

10 份 harness 對照文件

涵蓋 Claude Code、Codex、Pi、OMP、Peri、OpenCode、Gemini CLI、Crush、Cursor 與 generic。Peri 與 Claude Code 共用 skill 目錄。adapter 索引列出工具、模型與檔案位置。

先偵測，再讀 adapter

在 checkout 根目錄執行 bash scripts/harness-detect.sh --json。優先序是 --harness → PSTACK_HARNESS → 最近的祖先 agent 行程 → 環境標記 → 工作樹目錄 → generic。

每個 harness 一份模型設定

Claude Code 讀 ~/.claude/rules/pstack-models.md；Cursor 讀 ~/.cursor/rules/pstack-models.mdc。兩者由自己的規則系統載入。

其餘讀 ~/.agents/pstack-models.<harness>.md，缺檔才讀共享兜底 ~/.agents/pstack-models.md，並由常駐指令檔指向設定。

模型名稱不能跨工具照抄

Codex、Pi / OMP、Claude Code 各有自己的命名與推理預算格式。沿用該 harness 設定檔中的有效名稱；模型被拒絕時依 skill 的退回規則處理，並說明實際使用的模型。

舊版頁面記錄過 Linux VM 的 pi-task 與 dsh-home 副本。這些是個人派單環境，不是 pstack 的安裝前提；本次更新未重新檢查遠端副本版本。複製安裝需自行刷新，符號連結則跟隨其指向的 checkout。

2依情境選 skill

一般任務先用 /poteto-mode：說清楚目標與完成檢查，由它選 playbook。以下保留原本的 12 個常用入口，再補上設計、平行工作與進度回顧工具；這不是完整 skill 清單。

poteto-mode 任務入口

選擇符合任務的 playbook，依序執行其步驟與相關 skills。跳過的步驟留下原因。要它只規劃，就明說「先出計畫，暫不實作」。

來源：poteto-mode/SKILL.md

how 理解

回答「現在怎麼運作、程式該放哪一層」。追實際呼叫鏈與模組邊界，建立改動前的理解。

用法：/how session 恢復如何運作

why 原因

查 git、issue、文件與可用紀錄，回答「為什麼這樣設計」。區分有證據的結論與推測。

用法：/why cookie 校驗放在 Rust 層

teach 講解

視需要調用 how 與 why，再依讀者的理解順序講清楚子系統、變更或取捨。用來學懂系統。

用法：/teach 這次 runtime lookup 的設計

recall 跨對話回顧

從可存取的過往對話、共享紀錄與目前狀態重建某個主題的上下文。要接手特定分支，也可讓 poteto-mode 執行 Session pickup。

用法：/recall 上週的 runtime 工作

interrogate 對抗評審

由設定的評審獨立嘗試弄壞變更或設計。每項 finding 必須附真實執行的命令、實際輸出與應有結果；主 agent 重跑確認後才保留。只回報，不自動修碼。

新版已移除舊的四份 rubric / reviewer 參考檔；依 現行 skill執行。

blast-radius 連帶影響

追查小 diff 對外部呼叫方、設定或工作流程的影響。找出結論依賴的關鍵事實，再用實際執行確認。

用法：/blast-radius 這次 rsync 排除規則修改

tdd 測試先行

有便宜的本地測試路徑時，先建立修前失敗、修後通過的回歸測試。測試路徑不合適時，選最近的有效驗證方式。

用法：/tdd 修復 cookie 過期未報錯

principle-prove-it-works 驗實物

在實際使用路徑上檢查命令、畫面、儲存值或效能。完成報告應提供能支持結論的證據。

可直接說：套用 prove it works，展示真實輸出。

show-me-your-work 決策紀錄

長任務留下決策、理由、證據與結果，讓離開後的讀者能查核做過什麼，以及哪些事情仍待決定。預設用 decisions.tsv 或 .audit/<task>.tsv，以附加方式保留歷史。

用法：/show-me-your-work

figure-it-out 大型任務

為沒有現成做法的大型或跨模組變更設計嚴謹的執行方式，先定可檢查的完成條件，再用證據驗證假設。

用法：/figure-it-out 遷移這套 skill 載入方式

unslop 文字清理

刪除空泛詞彙、制式句型、模糊歸因與不必要的比喻，保留原意並配合原本語氣。README、PR 描述與對外文件都適用。

用法：/unslop 這段發布說明

reflect 改善 skill

使用者明確要求時，從會話提取能改變未來決策的教訓，提出具體 skill 修改。先審閱提案，再改副本；不得直接改外掛快取。

用法：/reflect；提案本身不代表修改已套用。

另外幾個值得直接指定的入口

釐清需求
/in-your-own-words 先重述目標；/sharpen 改善提示詞後交還，不執行提示詞中的任務。
設計與平行工作
/architect 定型別與模組形狀後實作；加 with checkpoint 可先審設計。/arena 多份同題嘗試後合併；/swarm 分塊或競賽並彙整結果。
本次對話回顧
/ketchup 整理自你上一則訊息後的變化與待決事項；/ketchup-video 把進展做成短字幕影片，待決事項仍以文字列出。影片需有可用的渲染工具。
更多入口
/technical-writing 寫技術文件；/benchmark-checklist 查核效能數字；/correct 防止重複犯錯；/poteto-help 按情境找工具。
單裝要帶上依賴：例如 why 會用 how，teach 會用 how / why，interrogate 現在依賴 arena 的派發與驗證步驟。不能假設裝了原先 12 個副本，就已具備新版完整工作流程；依 README 安裝表與各 skill 的相對連結檢查。

3任務提示詞：目標、完成檢查、證據

日常先交代想達成的結果，不必手工排列整串 skills。需要覆寫某一步時才指定 skill；一般由 poteto-mode 維持 playbook 的順序。

🐛 修 bug
/poteto-mode 修復 cookie 過期卻未報錯。先重現；完成條件是舊版失敗、新版通過，並附實際命令與輸出。
✨ 新功能
/poteto-mode 新增本地 runtime 設定。環境變數仍優先；檢查有效、缺失、損壞的設定，展示實際選到的工具。
🔧 重構
/poteto-mode 把載入邏輯集中到一個模組，行為不變。先保存目前輸出，再證明修改後一致。
🔍 調查
/poteto-mode 調查 session 恢復為何失敗。列出已知事實、證據與待驗假設，暫不改碼。
🧐 評審
/interrogate 檢查 git diff upstream main 與目前未提交的變更。只保留可執行重現的問題，暫不修碼。

Cursor 的 Custom Mode 可讓 poteto-mode 持續在上下文中。其他環境每個新任務重新指定入口，並使用該環境支援的持續執行能力。/loop 在 Cursor 與支援它的 Claude Code 環境可用，執行期限與停止條件依各自工具而定。

多任務編排已更新：Orchestrate 是 poteto-mode 的 playbook，沒有 pstack 自帶的 /orchestrate 指令。新版以 agent 工具、任務狀態與事件訂閱協調；舊 skills/poteto-mode/scripts/orch/ 已移除。跨 harness 時依 adapter 使用可用能力。

4派單紀律：把限制與驗收寫清楚

① 驗收沿真實使用路徑

完成後讀取實際產物、儲存值或命令輸出。退出碼與 agent 自述不足以支持驗收；模擬動畫中的數字也不能充當證據。

② 先寫清楚範圍

如果工作不能下載工具鏈、不能改產品碼，或只能出計畫，就在提示詞明說。驗證失敗要交代原因與影響，不能默默擴大範圍。

③ 證據可重現、可保存

長任務記錄命令、來源版本與證據位置。臨時目錄適合試跑；要交付的產物放到可持續保存的位置，並清理自己建立的程序與暫存。

5驗證：行為、形式化性質與 statechart

先分清楚要檢查什麼：真實使用流程由行為驗證驅動；競態、不變條件與狀態轉移可另建模型或使用程式驗證工具。形式化結論受模型、邊界與工具假設限制。

create-verification-skill

生成專案專用的驗證 skill，說明 Launch / Doctor / Drive / Evidence / Cleanup，並建立使用者功能地圖。把 skill 與 helpers 納入版本控制，交付證據或可重新產生證據的命令。

maintain-verification-skill

對照目前 app 更新驗證方法與功能地圖，回報 clean、changed 或 blocked。維護驗證時不順便改產品行為。

create-formal-verification-skill

挑 bug 代價高、一般測試難碰到的性質，依問題選工具，例如 TLA+ 或 kani。建立可失敗的檢查，記錄涵蓋範圍、假設與對應程式版本。

maintain-formal-verification-skill

程式變更後逐項查核規約與程式是否同步，區分 in sync、updated、bug、blocked。updated 與 bug 可同時成立。產品 bug 要報告；只有證據確認承諾刻意改變時才調整性質，不能為了過關而放寬。

/statechart：把 TLA+ 檢查結果畫成狀態圖

/statechart 使用 TLC 檢查 TLA+ 模型，產生 Mermaid 圖與報告，列出違反規則的路徑。它是獨立入口，與生成專案驗證 skill 的四個工具用途不同。

# 聊天提示詞範例
/statechart 為 runtime 選擇流程建立有界 TLA+ 模型。
明確寫出環境變數、本地設定與 mise 的優先序。
列出模型假設；若出現反例，依路徑在真實程式重現。

# 從 checkout 執行既有規約；SPEC.tla 與輸出目錄請換成實際路徑
skills/statechart/scripts/statechart SPEC.tla --config SPEC.cfg --out /path/to/new-output

runtime 選擇順序

TLA2TOOLS 明確指定 jar 時優先，JAVA 可覆寫 Java。否則先讀 $XDG_CONFIG_HOME/statechart/runtime.json；檔案不存在才讀 ~/.config/statechart/runtime.json，都沒有才用 mise。

本地 JSON 的 jar 與 java 都要是絕對路徑。既有設定無效就停止；走 mise 的首次執行可能安裝 TLC / Java，需要網路。

讀懂結果的邊界

超過 500 個模型狀態時，圖只保留違規路徑；若沒有規則違反，就不產生 chart.mmd，仍需閱讀報告。未檢查的規則不等於通過。

模型描述程式時，必須把反例逐步回放到真實程式。反例無法重現，就先查模型是否錯了。需要圖片時依 render 參考文件使用 Pele。

VCLI 可選的起點：X11 cookie / session 狀態與並發可先建有界 TLA+ 模型；Rust unsafe 區段可評估 kani；「舊結果檔不得被評分」可寫成不變條件。這些是候選驗證題目，尚未代表對應專案已完成驗證。

可查閱 statechart 用法與 runtime lookup 範例。範例模型通過，只能支持它明列的選擇策略與邊界，不能推論所有檔案系統或工具環境都正確。

6上手三步

安裝並設定

安裝所需 skills 與依賴，執行 /setup-pstack。在新對話確認 harness 與模型設定已載入。

選一個能驗收的任務

用 /poteto-mode 加目標、完成檢查與限制。跨 harness 時先讀 adapter；沒有 app 驅動方法就先建立 verification skill。

核對證據，再沉澱教訓

看真實輸出與未檢查項目。長任務用 /show-me-your-work 留紀錄；需要改善 skills 時再明確要求 /reflect。

7鏡像維護：pull 與同步 Cursor 是兩件事

git pull --ff-only origin main 更新 deanyou/pstack 已發布的內容。要把 Cursor 的新內容帶進鏡像，依 MIRROR.md 先更新 upstream，再合併 main，保留這個鏡像的修改。

upstream 保持原樣

upstream 保存 Cursor 的 pstack 樹；main 加上 harness 適配與自有內容。排除清單從 main 讀出，不能假設 upstream 上也有同一份檔案。

/scripts/ 必須錨定根目錄

mirror-paths.txt 用 /scripts/ 保護鏡像根目錄腳本。寫成 scripts/ 會把巢狀的同名目錄也排除，曾漏同步 statechart runtime 與 poteto-mode 工具更新。

比內容，不只看版本號

同步後核對 upstream 與 Cursor 的實際樹，重查 harness 編輯與 bundled prompt，並執行 node --test scripts/sync-exclusions.test.mjs。沒有新內容就不造空提交。
