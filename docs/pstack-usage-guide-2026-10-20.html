PSTACK · Agent Engineering Skills

让 agent 写更少、但更高质量的代码

pstack 是 poteto（React 核心团队、曾在 Meta / Netflix / Cursor 工作）每天用来交付高质量代码的一套 Agent Skill。核心理念：吞吐量没有质量毫无意义——先钻深，再求快。当 agent 能写出可验证的好代码，你才敢真正并行派发多个 agent，这就是 poteto 说的 fearless parallelism。

212 个 skill：按用途认领

每个 skill 都是一个独立的工作流说明书。agent 读到它，就按里面的步骤干活。

how 理解

回答"X 是怎么工作的"。改代码前先做代码走读：子系统架构、运行时流程、归属/分层问题（"这该放哪层""哪个包拥有它"）。产出是资深工程师 onboarding 级别的心智模型，不是注释版源码。

触发：改动前先理解 · "how does X work" · "where should this live"

why 理解

回答"为什么长成这样"。how 的搭档：how 讲代码做什么，why 讲什么力量把它塑造成这样。并行查证据（git、issue、文档、聊天记录、可观测性、错误追踪），区分"我知道"和"我在推测"，带置信度措辞输出。

触发：设计依据 · "why we picked Y" · 回归复盘 · 阈值从哪来

teach 理解

把一坨工作讲到人真懂。跑一遍 how + why，再编织成按你节奏的 plain 讲解。目标是理解，不是改代码。适合接手陌生子系统。

触发："teach me this" · "help me really understand X"

recall 理解

开工前先重建上下文：从聊天记录、实时状态和共享记录里拼出"现在到哪了、下一步是什么"的紧凑简报。别只看自己的 transcript——长 bug 尾巴的故事多半在别人的 issue 和聊天里。

触发："where did I leave off" · "catch me up"

interrogate 评审

多模型对抗评审：每个配置的模型拿同一份 prompt + rubric，从独立角度撕你的改动。对抗信号来自模型多样性，不是分配人设。产出是综合裁决，不自动改代码。

触发："tear this apart" · "find blind spots" · stress test

blast-radius 评审

找出改动在 diff 之外会炸掉什么。列调用方不算本事（grep 一秒的事），本事是找出 grep 看不见的 breakage。关键纪律：别信自己的分析报告——把结论依赖的一两个事实找出来，用跑真代码证明，而不是写下来。

触发："what could this break" · 评审不放心的小 diff

tdd 工程纪律

先让 bug 可执行：有便宜的本地测试路径时，先写出"修前失败、修后通过"的聚焦回归测试再动生产代码。没便宜测试路径时别硬造——用最近的可用验证代替。

触发：修 bug 且有明确便宜测试 · 回归测试

principle-prove-it-works 工程纪律

收工前验实物：对着真实产物验证，不认代理指标——不看"编译过了"、不看 agent 的自我报告。跑起来、走完真实路径、读实际值。验证失败先怀疑观测方法，再怀疑系统。

触发：任何任务收尾 · 验收标准

show-me-your-work 工程纪律

长跑/无人值守任务留可审计的决策轨迹：一个 TSV，一行一个决策（时间、阶段、做了什么、为什么、证据指针、结果）。证据是 commit SHA、文件行号、产物路径，不是段落。

触发：/show-me-your-work · 多阶段任务 · 离开后回来要能审计

figure-it-out 工程纪律

没有现成 playbook 时先设计 playbook 再动手：大迁移、多部件改动。先给出可证伪的完成定义、量化 scope、定严谨度（宁高勿低），跑假设循环，全程记决策日志。

触发："figure it out" · 大迁移 · 无章可循的大改动

unslop 写作

删 AI 腔：扫固定模式并重写——"delve / crucial / tapestry"类词汇、"serves as"式花哨 is、"Not just X, but Y"句式、硬凑三段式、"Experts believe"式模糊归因。保义、合语气。

触发：任何对外文本 · 新功能交付默认挂上

reflect 反思

只在你说 reflect 时用：起三个并行评审 agent 挖当前会话的 durable 教训，每条教训落成对某个 skill 的具体修改。一次性经验不算教训，不写进去。

触发：你亲口说 reflect

4三个实战教训（你亲授）

① 验收只认实物

prove-it-works 落到派单：验收看 session 文件的新活动和产物文件本身，不认 exit 0 / "completed"。快得可疑的完成是去验证的信号，不是放行的信号。

② 派单写负约束

prompt 里写明"不许装工具链/包，做不到就报告收工"。否则 agent 会自作主张扩 scope——pi 曾花十几分钟装 rustup。

③ prompt 与产物放 ~/workspace

别放 /tmp：VM 替换会清空，曾导致续跑命令静默失败。每次复核完往 ~/workspace/pi-quality/quality-log.tsv 追加一行。

7深挖：四个 verification skill = VCLI Verifier 的操作化版本

四个 skill 组成一个完整的 verifier 闭环，恰好是你 VCLI 架构里 Generator / Policy / Executor / Verifier 的操作化形态。fork 的 README 也明确把 create 与 maintain 标成成对安装——生成 + upkeep，本来就是一个闭环的两半：

create-verification-skill

生成"像用户一样驱动真实 app"的行为验证 skill：Launch / Doctor / Drive / Evidence / Cleanup + feature map。对应 VCLI 的行为层验证（virtuoso-cli 走 PTY 驱动、跑真实命令、留证据）。

create-formal-verification-skill

生成形式化验证 skill：选"bug 代价最大、测试最够不到"的代码，问题选工具（TLA+ / kani / bend）。对应 VCLI 的性质层验证（不变量、并发正确性）。

maintain-verification-skill

upkeep 循环，结果三分类：clean / changed（一个 PR 修 drift）/ blocked。只改验证，不改产品代码。

maintain-formal-verification-skill

upkeep 循环，结果四分类：in sync / updated / bug / blocked。这套分类可以直接借给 RSI / DNW runbook。

纪律 1：Able to fail

每个 check 必须在故意弄坏的代码变体上失败过一次。没见过它失败的 check 证明不了任何事——这是 verifier 版的 prove-it-works。

纪律 2：Sync commit

每个 check 记录"上次确认描述的是哪个 commit 的代码"。代码变了、验证没跟上还继续 pass，是最危险的情况：看起来像证明，其实描述的是不存在的代码。这就是你的"验证履历"。

纪律 3：不准放宽性质

验证失败时不准弱化性质/模型去让它过；maintain run 不准改产品代码，bug 只报告。drift 和 bug 必须分开说——这就是"AI 找可疑、确定性工具定罪"。

给你的三个具体靶子：① virtuoso-cli 的 x11.rs（X11 cookie/会话状态机 + 并发）→ TLA+ 的完美靶子：bug 代价大（你刚修了两个）、测试够不到；② Rust bridge 的 unsafe/内存行为 → kani；③ Rule2DRC harness 的 fail-closed（"旧结果文件不能被打分"）→ 本身就是一个 invariant，可以形式化。
